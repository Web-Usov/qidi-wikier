# Архитектура QIDI Wikier

## Цель

Превратить Telegram-выгрузки QIDI-сообщества в проверяемую редакторскую базу знаний, сохранив provenance и не выдавая одиночное мнение, автоматическую связь или кластер за подтверждённый факт.

## Слои

1. **Источники** — неизменяемые Telegram JSON.
2. **Точные обсуждения** — цепочки только по `reply_to_message_id`.
3. **Контекстный граф** — отдельные нетранзитивные предположительные рёбра между верхнеуровневыми сообщениями.
4. **Evidence-кандидаты** — структурированные технические случаи из точных цепочек.
5. **Knowledge-кластеры** — детерминированные редакторские очереди совместимых evidence-кандидатов.
6. **Проверенные доказательства** — результат ручной проверки исходного текста, параметров и ограничений.
7. **Карточки знаний** — законченные выводы с окончательной надёжностью и ссылками на доказательства.

## Конвейер

```text
Telegram JSON
  ↓ потоковый парсер и нормализация
консервативная фильтрация
  ↓
точные reply-цепочки
  ├─→ нетранзитивный context graph
  └─→ evidence schema v3
          ↓ несколько источников
      knowledge cluster schema v2
          ↓ ручной аудит
      проверенные доказательства
          ↓
      карточки знаний
```

## Инварианты

- Точная reply-цепочка после построения не расширяется эвристикой.
- Предположительное контекстное ребро не влияет на следующие решения inference.
- Контекстное ребро не является доказательством.
- Evidence всегда содержит исходные сообщения и их provenance.
- Knowledge-кластер всегда имеет `review-required` и `unrated`.
- Автоматизация не назначает карточкам уровни `A/B` и не формулирует техническую истину.

## Контекстный граф

Используются временной разрыв, автор, материалы, принтеры, компоненты, бренды, содержательные ключевые слова и ответные маркеры. Жёстко отклоняются конфликты основных материалов и принтеров, дубли, соседние вопросы разных авторов и неоднозначные лучшие кандидаты.

Для каждой принятой связи сохраняются score, margin, confidence, положительные и отрицательные причины. Связь существует только как независимое ребро.

## `knowledgeValue`

`knowledgeValue` оценивает пригодность точной цепочки для дальнейшего аудита: наличие технических сущностей, параметров, вопроса, ответа, рекомендации или результата. Он не означает истинность и не используется как уверенность контекстного ребра.

## Evidence schema v3

Evidence-кандидат создаётся из точной цепочки с достаточным `knowledgeValue` и содержательностью. Он хранит:

- `sourceName`, стабильные evidence/thread/root ID;
- полный список исходных сообщений;
- `author`, `authorId`, дату, `replyTo`, исходный текст и `hasMedia`;
- материалы, семейства материалов, основной материал, принтеры, компоненты и бренды;
- дословные температуры, скорости, расходы, размеры, проценты, длительности и версии;
- типы `question`, `observation`, `answer`, `recommendation`, `result`, `configuration`, `reference`;
- статус `ready`, `question-only`, `needs-context` или `reference-only`;
- предварительную надёжность `C/D` и флаги проверки.

Предварительный `C` возможен только для собственного follow-up результата с явным исходом и параметрами непосредственно в сообщении результата. Пересказы производителя, поддержки, продавца или нейросети остаются `D`.

## Knowledge cluster schema v2

Агрегатор читает evidence из нескольких источников и формирует только редакторские очереди.

Ключ кластера строится по корневому сообщению случая. Поздний ответ может быть поддержкой или предостережением, но не меняет тему, материал или принтер корня.

Evidence получает одну роль:

- `support` — `ready` без известных автоматических предостережений и с человеческим содержательным ответом;
- `caution` — медиа, торговая/внешняя ссылка, нейросеть, пересказ внешнего источника или автоматический бот-ответ;
- `unresolved` — вопрос без ответа или недостаточно завершённый случай.

High-priority требует одновременно:

- минимум два поддерживающих evidence;
- минимум два независимых автора ответа;
- минимум два различных fingerprint ответа;
- минимум два источника;
- не менее половины evidence в роли support;
- ограниченный размер очереди;
- когерентность всех поддерживающих корневых сообщений и хотя бы одну когерентную межисточниковую пару.

`high` — только порядок ручной проверки. Он не является уровнем надёжности.

## Контроль качества

Каждый слой выпускает полные JSONL и стратифицированные Markdown-выборки:

- `review/context_graph.jsonl`;
- `review/context_links_sample.md`;
- `evidence/candidates.jsonl`;
- `review/evidence_candidates_sample.md`;
- `knowledge/clusters.jsonl`;
- `review/knowledge_clusters_sample.md`;
- статистику и manifest.

Регрессии из реальных выгрузок закрепляются тестами. GitHub Actions сначала выполняет syntax check и тесты, затем четыре `ingest`, агрегацию и публикацию artifact. Производные файлы вручную не редактируются.
